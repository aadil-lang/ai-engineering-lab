# Engineering Lab Workflow Guide

This document defines the standard operating procedures for Antigravity agents when utilizing the Engineering Lab for independent verification, regression analysis, and failure remediation.

---

## 1. Principles of Independent Verification

1. **Separation of Author and Validator**: The agent writing the application code cannot serve as the sole validation authority. Local unit tests verify that the code compiles and passes author-specified assertions, but they do not prove that end-to-end user workflows or application reliability properties hold.
2. **Authoritative Evidence**: Claims of correctness must be supported by empirical evidence generated by the Engineering Lab (test execution logs, HTTP status codes, screenshots, DOM trees, and failure diagnoses).
3. **No Phantom Passes**: If the Lab has insufficient data to verify behavior, report `VERIFICATION_INCONCLUSIVE`. Never convert an unknown state or abstention into a pass.

---

## 2. The 12-Step Lifecycle in Practice

### Phase 1: Planning & Implementation (Steps 1–3)
* **Step 1: Understand the Task**: Identify the application under test (e.g., `app_inventory`, `app_eda`, `app_booking`), the required functional change, and expected reliability impacts.
* **Step 2: Inspect Repository**: Review relevant routes, controllers, and models. If needed, call `inspect_application` via MCP to understand existing registered endpoints and runtime configuration.
* **Step 3: Implement Change**: Write the minimal, robust code patch.

### Phase 2: Local Verification (Steps 4–5)
* **Step 4: Run Local Tests**: Execute project unit tests (e.g., `python -m pytest backend/tests` or relevant component tests) in the Antigravity terminal.
* **Step 5: Inspect Local Results**: Ensure that all unit tests pass without errors or regressions. If a unit test fails, fix it immediately before contacting the Engineering Lab.

### Phase 3: Independent Lab Verification (Steps 6–7)
* **Step 6: Request Lab Verification**: Initiate a behavioral test session in the Engineering Lab using `start_test_session`:
  ```json
  {
    "application_id": "app_inventory",
    "scope": "SMOKE",
    "idempotency_key": "verify-inventory-patch-001"
  }
  ```
  Or inspect live runtime health via `get_application_health`.
* **Step 7: Inspect Evidence**: Check the returned `ToolEnvelope`. Inspect `status`, `summary`, and test outcome statistics.

### Phase 4: Failure Remediation Loop (Steps 8–10)
If the Engineering Lab discovers a test failure:
* **Step 8: Retrieve Failure Telemetry & Evidence**:
  1. Call `list_failures` to identify failure IDs associated with the current session.
  2. Call `get_failure` with the specific `failure_id` to retrieve stack traces and failing step actions.
  3. Call `get_evidence` to retrieve DOM snapshots, console logs, or network telemetry.
  4. Call `diagnose_failure` to receive epistemic root cause attribution.
* **Step 9: Fix the Defect**: Implement the necessary code correction based on observed evidence rather than conjecture.
* **Step 10: Re-run Local Tests**: Confirm locally that unit tests continue to pass.

### Phase 5: Independent Re-Verification & Closure (Steps 11–12)
* **Step 11: Independently Verify in the Lab**: Execute a new test run in the Engineering Lab (with a fresh idempotency key):
  ```json
  {
    "application_id": "app_inventory",
    "scope": "SMOKE",
    "idempotency_key": "verify-inventory-patch-002"
  }
  ```
  Verify that the previous failure condition is completely resolved and that no secondary regressions occurred.
* **Step 12: Report Evidence**: Formulate the final completion report using the structured Engineering Trace format.

## 3. Failure Remediation Flowchart

```text
[ Engineering Lab Test Fails ]
               │
               ▼
     Call `get_failure`
(Inspect stack trace & action sequence)
               │
               ▼
     Call `get_evidence`
(Examine DOM, screenshot, network log)
               │
               ▼
    Call `diagnose_failure`
(Evaluate OBSERVED vs INFERRED root cause)
               │
               ▼
     Patch Code in Antigravity
               │
               ▼
      Pass Local Unit Tests
               │
               ▼
   Call `start_test_session` (New run)
               │
               ▼
   Verify Evidence Resolves Failure
```

---

## 4. Operational Invariants

* **Never reuse idempotency keys across different code changes**: Idempotency keys must be distinct per verification attempt to prevent deduplication against earlier runs.
* **Never suppress diagnostic warnings**: If `get_uncertainty` flags covariate shift or high variance, highlight this risk to the developer even if all functional tests pass.
