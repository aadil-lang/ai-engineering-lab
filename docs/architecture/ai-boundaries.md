# AI Authority Boundaries in Engineering Lab v1

## Core Invariant

> **LLM output is an input to the engineering system, not an authority over the engineering system.**

In Engineering Lab v1, artificial intelligence models (such as local Qwen2.5-Coder instances or agent evaluators) operate strictly as **exploratory, diagnostic, and advisory instruments**. They never possess autonomous authorization authority.

---

## 1. What AI May Do

AI agents and models within the Engineering Lab are explicitly permitted to:

1. **Interpret Evidence**: Analyze multi-modal evidence packages (DOM snapshots, network logs, error stack traces, console exceptions) to infer probable failure modes.
2. **Propose Browser Actions**: Suggest exploratory UI navigation paths, form inputs, and boundary-value test sequences during exploratory sessions.
3. **Explore Applications**: Interact with authorized staging and dogfooding application targets within predefined session and budget bounds.
4. **Propose Diagnoses**: Formulate causal hypotheses explaining observed discrepancies between expected and actual behavior.
5. **Propose Remediation**: Generate candidate code diffs, configuration adjustments, and prompt modifications for human review.
6. **Use Retrieved Engineering Memory**: Consume historical failure patterns and past remediation outcomes retrieved via local hybrid RAG.
7. **Propose Prompt Improvements**: Suggest sliding window token buffers, few-shot demonstration adjustments, and structured output schemas.
8. **Summarize Engineering History**: Synthesize cross-run telemetry and historical stability trends into readable engineering briefs.

---

## 2. What AI May NOT Independently Authorize

AI models and autonomous agents are **strictly prohibited** from independently executing or authorizing:

| Prohibited Action | Governing System Authority |
| :--- | :--- |
| **Production Code Changes** | Human Governance Board / Authorized Software Engineer |
| **Pull Request Merges** | Human Repository Maintainer |
| **Production Deployments / Releases** | CI/CD Pipeline & Human Release Manager |
| **Prompt Template Promotion** | Prompt Lab Governance Gate & Human Approver |
| **Model Version Selection / Promotion** | Human Engineering Leadership |
| **Retrieval Strategy / RAG Re-indexing Changes** | System Administrator |
| **Tool Permission Granting / Escalation** | Control Plane Security Boundary & Operator Config |
| **System Rollbacks** | Human Operations Lead |
| **Governance Policy Overrides** | Immutable Deterministic Policy Engine |

---

## 3. Human-in-the-Loop Governance Guardrails

All proposed code fixes, prompt updates, or infrastructure changes generated by AI must proceed through the **Deterministic Governance Gate** (`backend/app/governance/`):

1. **Risk Scoring**: Deterministic assessment calculates blast radius, regression probability, and cold-start uncertainty.
2. **Evidence Packaging**: An auditable evidence package containing reproduction runs, DOM diffs, and proposed code patches is compiled.
3. **Human Authorization**: An authorized engineer must cryptographically record an approval decision before any change is applied.
4. **Independent Retest**: The applied fix is tested in a separate, isolated run to verify remediation before any candidate PR is updated.
